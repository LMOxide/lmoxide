# Effect browser: hand-off for a separate web app

A small web app for browsing the game client's effects (and later looks and animations) and
previewing them **in the running game client**, so the user can point at the exact effect they
remember ("this one plays when a minifigure is smashed") instead of describing it.

The game data formats (meshes, particle systems, EMotionFX animations, Scaleform UI) are not
rendered in the browser: the app lists and searches the catalog, and a "Preview" button makes the
user's own character play the effect in the client, through the LMOxide REST API.

## Prompt for the new repo

> Build a small web app, "LMOxide effect browser", in this repo. It talks to the LMOxide REST API
> (`lmoxide-api`, default `http://<server>:8090`; contract in LMOxide's `docs/openapi.json` and
> `docs/API.md`, auth as in `docs/WEB-UI.md`: log in with an admin account and send the session
> token as `Authorization: Bearer <token>`, or use an API key with admin scope).
>
> Data: `GET /v1/catalog/effects` returns `{effects: [...]}`; each entry has `id`, `kind`
> (`effectpackage` or `particlesystem`), and for packages `timelines` (type: particle, sound,
> emotionfxattribute, lua, ...; name, start and duration in seconds, target), `particles`
> (particle resource names or ids), `sounds` (.wav paths), `animation_attributes` (e.g.
> `limbostart`), `code_hooks`, `lua` (snippets, e.g. camera shakes), `looping`, and `used_by`
> (items and spells that mention the id, with their names; may contain a few false matches).
> Packages have no names of their own: show the `used_by` names, the sounds and the particle
> names as the description.
>
> Features:
> 1. A searchable, filterable list: free text over id, used_by names, sounds, particles, Lua;
>    filters for kind, timeline types (has sound / particle / animation attribute / Lua),
>    looping, used or unused. Sort by id. Show the timeline as a small bar chart (start/duration).
> 2. Pick the player to preview on: `GET /v1/players` (online players: account_id, username,
>    character name). Remember the choice.
> 3. Preview: `POST /v1/players/{account_id}/command` with `{"command": "!fx <id>"}` plays the
>    package on that character in the game (others nearby see it too). Also buttons for
>    `!fx <id> <hook>` (code hooks listed in the entry), `!fx stop`, and keyboard shortcuts for
>    next/previous in the current filtered list (send `!fx <id>` for the neighbour, so stepping
>    follows the filter). The player needs GM level >= 1 for test commands.
> 4. Other previews through the same endpoint: `!skin <monster data id>` / `!skin reset` (look
>    like any monster) and `!state <n>` (character state, stat BCCState: 1 normal, 29 Limbo =
>    smashed, 104 building). A free-text command box for any other test command.
> 5. Notes: mark entries (e.g. "smash effect", "not it", free text) and export the notes as JSON or
>    Markdown, to hand back to the LMOxide developer. Store notes in localStorage.
>
> Keep it a static single-page app (no backend of its own); configurable API base URL. If the API
> lacks something you need (e.g. a catalog of monster data looks or animations), write down the
> proposed endpoint instead of working around it; it will be added in LMOxide.

## What exists on the LMOxide side

- `GET /v1/catalog/effects` (scope read): `data/effect_catalog.json`, generated by
  `tools/re/py extract_effect_catalog.py` (about 2.2 MB; 2518 packages, 4 particle systems in
  RDB 1000622; the scan for `used_by` takes ~10 minutes, `--no-refs` skips it).
- `POST /v1/players/{account_id}/command` (scope admin, audited): runs a test command as that
  player through the game server's control interface; `tools/dev-command.sh <account> '<cmd>'`
  does the same from a shell.
- Test commands (devcmd.rs): `!fx <id> [hook]`, `!fx next|prev|stop` (steps through every
  package in id order), `!skin <monster data|reset>`, `!state <n>`, `!spawn [count] <name>`, and
  the rest in [DEVELOPMENT.md](DEVELOPMENT.md#test-commands). The command answer has `replies`:
  the chat lines the command produced.
- `GET /v1/catalog/test-commands` (scope read): everything the test commands accept (commands,
  `!goto` targets, `!test` scenarios, dialogues, loot kinds, spawnable names, monster data looks).
- Local backend for development: `tools/web-dev-backend.sh` (API on :8090 with demo accounts);
  previews need a running game server and a logged-in client, e.g. the LAN server
  (`tools/lan-server.sh`).

## Possible next catalogs

Animations (EMotionFX motion names a package's attributes switch), spells with their effect
packages, monster data looks beyond what is placed in the world. The browser's
`docs/API-PROPOSALS.md` lists what it still asks for.
